# 自博弈方案：让程序自己试，先验证是否划算

状态：仅设计，尚未实现模拟器或启动训练。基于上游 `7e62942` 与本地基线 `9c263d6`。用户本轮要求先评估设计，避免高成本、耗时的训练与资料整理。

## 结论

可以设计自动练习、对战和改进的流程。用户不需要先提供大量专家打法；需要的是让动作得到可信结果的环境。当前资料足够做局部练习环境，尚不足以保证完整复刻正式判题器。

首选路线：基于现有 Bot 的少量策略参数自动试验 → 得到校准过的环境和改进证据 → 必要时训练小型决策模型。先做能检验想法的版本。

## 1. GAN、自博弈与“自己学”

- GAN 训练生成器和判别器，用于学习数据分布；它的对抗机制不能直接等同于两个游戏选手学习获胜。[GAN 原论文，2014](https://arxiv.org/abs/1406.2661)
- 自博弈强化学习通过对局结果改进决策，可以减少对专家棋谱和手写打法的依赖。AlphaZero 是已验证的例子，但有可执行的游戏规则和大量对局。[DeepMind，2018-12-06](https://deepmind.google/blog/alphazero-shedding-new-light-on-chess-shogi-and-go/)
- MuZero 可以从交互中学习用于规划的模型，不需要事先给出完整动态规则，但仍需要环境提供观察和奖励。[DeepMind，2020-12-23](https://deepmind.google/blog/muzero-mastering-go-chess-shogi-and-atari-without-rules/)

这些研究说明路线可行，不证明本比赛能用同样成本得到同样成绩。本文的小步方案是针对本项目的工程判断。

## 2. 运行机制知道多少？

回合循环大致是：

1. 判题器给双方各自可见的状态。
2. 双方分别为角色/炮台返回动作，可附带 LLM 请求或任务沙盒命令。
3. 判题器执行合法性、移动碰撞、攻击与其他动作结算。
4. 世界进入下一回合，返回新状态、动作结果和工具结果。
5. 达到终局条件，按基地情况、积分与换边规则判胜负。

对自行编写训练环境的影响：

| 机制 | 当前信息 | 可以做什么 |
| --- | --- | --- |
| 地图尺寸、8 向移动、切比雪夫距离、昼夜和上限 | 文字规则较明确 | 实现并做边界检查 |
| HP、造价、升级、炮台伤害及冷却 | 有规则，部分请求示例与正文矛盾 | 配置化；正式输入和回放用来核对 |
| 建造区域、机器人出生位置/波次数量/寻路/选目标 | 不完整，部分建造信息在外部图片里 | 只做明确标注的假设，不能当作官方事实 |
| 同时行动的完整结算顺序、细节 | 有部分顺序说明，不是完整引擎实现 | 用关键单步回放校准 |
| 新闻、宝藏、真实任务生成与答案判定 | 主要是概述/示例 | 不伪造真实能力评估 |

若训练环境错误地让机器人只走一条路，模型可能学会堵住这条路，在训练中高胜率，正式比赛却失效。多种合理假设可以检验策略是否脆弱，无法替代真实环境验证。

## 3. 最小方案

### A. 先做局部练习场

最小范围是一个夜晚：给定双方基地、防御工事、角色和机器人波次，推进 60 个夜间回合。保留两个玩家视角、同时行动和法定可见信息。程序不得读到正式接口不给它的敌方隐藏状态。

在局部版本里先比较目标选择、炮台配合和防线布置。初始等级/配置可作为场景输入；没有模拟白天成本时，不能据此宣称某个升级顺序或完整经营策略最好。

未知波次和路径先设少量可替换假设，并把结果标为“局部模拟”。有官方引擎时优先接入引擎，避免另维护一套规则。

### B. 首轮用自动试策略，降低试错成本

从已有 Bot 出发，固定寻路、接口与动作合法性处理，只让少量参数变化，例如：

- 优先攻击离基地近的目标，还是已受伤目标。
- 火箭选择密集落点的权重。
- 分配炮手时，对距离与现有站位的偏好。

建立若干候选配置，对相同场景和不同侧位置运行，保留表现较好的配置，再做小幅变化。第一批产物是策略配置和比较结果，不声称已经训练出神经网络。

对手保留当前基线和几个固定旧版本。先能稳定抵御机器人，再逐步加入对手干扰；只战胜自己的最新副本，不足以证明整体变强。最终选出的版本还要跑未用于选参的场景与对手，保留原基线供回退。

### C. 有收益后再决定是否训练小模型

只有环境已校准、每秒推进回合数足够、简单选参已表现出限制时，才进入神经网络训练。初步候选是带合法动作约束的强化学习策略；具体算法和库在启动该阶段时再核对选型。

输入采用比赛可见状态，例如基地血量、金币、昼夜、角色位置、可见敌人和炮台情况。先输出有限的高层选择：防守目标、角色分工、是否回防、下一项建设。底层代码负责执行和合法性。必要时保留观测历史处理隐藏敌人，不能直接套用完全信息棋类的搜索假设。

目标遵循官方胜负；生存和积分作为辅助诊断，不能把“多采矿”“多开火”之类容易刷的过程指标当成最终成功。局部夜战的血量/存活指标仅用来筛选局部能力。

本地策略模型如果最终生成，将是比赛程序中的独立推理文件；能否随提交包携带及运行，需要提交环境确认。训练代码、候选模型和最终参赛程序分开。是否值得训练，由实测成本和增益决定。

### D. 文字任务另行验证

新闻解读、跨天线索和沙盒解题继续利用比赛提供的 LLM 通道。游戏对战产生的数据，不能凭空给出未知任务的正确答案。

获得少量代表性任务及可靠评分后，可以自动生成有程序校验答案的练习变体，用于改进提示词和脚本。生成者自己的评价不作为唯一正确性依据。首轮战斗试验不调用付费 LLM；若省略或固定任务收益，结果只适用于这个受限实验。

## 4. 成本和停止条件（提议，尚未执行）

- 先测两场的实际推进速度，按“场次数 × 每场耗时”估算费用与时间；网络沙盒或 LLM 延迟需另计，不能用本地 Bot 的 0.8 ms 代替环境速度。
- 第一批以本机 CPU、最多 30 分钟运行时间或 80 个局部场次为上限，含测速，以先到者为准；这是试验上限，不是保证达到强模型所需时间。实现环境的开发时间单独说明。
- 原型不请求 GPU、不安装训练框架，不产生付费模型调用；更大规模是有证据后的另一个决策。
- 训练/选参场景与最终检查场景分开。少量场次只能提供方向信号，不据此宣布可靠胜率。
- 没有跨场景改善、只在单一假设上获胜、或环境过慢时，停止扩大训练；先检查规则或保留简单策略。
- 最终提交前必须在官方环境验证。离线回放只能核对已发生的动作及结果，不能直接知道另一个动作会发生什么。

## 5. 最少需要用户提供什么？

设计和局部原型不需要额外材料。无需用户先写打法、做大批标注或整理全部资料。

最有价值的一项是能反复运行的官方比赛程序/试跑入口。即使是只能输入动作、返回结果的黑盒，也能用于采集经验；训练规模取决于调用速度、额度和重置能力。

如果只有一份真实回放，仍能校准其中出现的机制，无法完全确认未出现的机制或任意新动作。届时只追问影响当前实验的具体缺口。任务样例等材料留到真正优化任务模块时再获取。

- 查询入口与来源：上文 GAN 原论文（2014）、AlphaZero 官方说明（2018-12-06）、MuZero 官方说明（2020-12-23）；[MuZero 论文](https://arxiv.org/abs/1911.08265)提交于 2019、v2 为 2020。
- 采用结论：自博弈能减少专家策略数据依赖，但仍需要可信反馈；学习环境模型也需要真实交互经验。
