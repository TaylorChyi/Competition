# 阵营修正与自对弈迭代结果

> 历史记录：本报告对应 `2f71866` 及更早实验；当前算法与十晚结果见 [最新迭代报告](十晚生存迭代.md)。

日期：2026-09-18。交付包：[Latest Release / 带版本号参赛包](https://github.com/TaylorChyi/Competition/releases/latest)。

## 交付结论

**修复了夜间把对方的机器人也当成攻击目标的问题。第二晚生存问题尚未解决。**

本版仍使用一座加特林、一座电磁炮、一座火箭炮，在进攻我方的机器人中选最近目标。两轮实验分别选出的“增加火箭”和“内侧站位＋三火箭”方案，都没有在独立场景中改善生存表现，因此未替换默认策略。

用户确认上一版 `1ff259b` 的包已经可以在内网平台启动，本版沿用单一 `CoreGeek/` 目录和 `CoreGeek/main3.py` 入口。新算法还没有正式平台回放或成绩。

## 修正了什么

旧程序解析了机器人位置、血量，却没有保存 `robot.targetTeam`，选敌时直接从所有机器人中取最近的一个。现在读取 `teamOur.type`，三种武器以及可选火箭范围评分都只使用目标阵营与我方一致的机器人。换边时按当前请求重新判断，不依靠地图方位或缓存上一局阵营。

所有机器人仍参与移动避障。缺少有效阵营字段时不猜测攻击目标；回合日志增加 `team`、`incoming`、`unknown_target`，方便从正式状态检查字段是否完整。

这是**选敌修正**。加特林 / 电磁炮的弹道可能被其他机器人截住，火箭也可能溅射其他机器人；本版没有实现完整弹道避让。在第二轮复核中，混合炮台仍出现 2 次实际只打到对方机器人，来自模拟弹道遮挡，不是主动选择对方目标。

源码：[协议解析](../CoreGeek/src/agent/protocol.py)、[决策](../CoreGeek/src/agent/brain.py)、[日志](../CoreGeek/src/agent/server.py)。

## 实验怎样运行

两轮共 **96 场本地自对弈**，另有 4 场预跑；两轮分别耗时 27.26 秒和 26.43 秒。没有训练神经网络、调用外部模型或使用 GPU，本轮做的是少量策略配置的自对弈比较。

- 新策略与上次发布的 Bot（提交 `1ff259ba593446295739b045060648b3cce997ba`）在同一张地图同时决策，并交换双方席位。
- 从 75 金币、基地 1500 HP、两名工人和一名先锋开始。炮台由实际 Bot 指令建造，初始没有炮台，新建炮台一级。没有给候选免费二级装备。
- 最多连续运行三晚，共 390 回合。金币、背包和建筑损伤跨天保留；旧机器人天亮清除，死亡角色在下一白天 20 回合后复活。基地被毁后该侧停止发指令，继续记录到预定回合，故统计不是官方比赛胜负。
- 每轮先用 2 个训练种子、2 种模型、双方席位比较 4 个候选，共 32 场；选定配置后，用新的 2 个种子复核候选与仅修阵营的方案，共 16 场。
- 波次使用独立的种子，避免某个策略采矿次数不同，意外改变后面的机器人波次。
- 优先比较生存指标，再看剩余基地血量。第二轮按最差模型的两晚生存率、存活夜数、存活回合、最终基地血量排序。复核失败不会自动修改默认策略。

这是一套简化的共享地图环境。随机波次数量、出生点、机器人寻路和遇墙行为尚未由官方引擎确认；没有任务奖励、新闻、宝藏、交易、升级、召唤、玩家直接交战或完整官方计分。**以下百分比都是本地场景统计，不能当作比赛胜率。**

## 第一轮：环境太容易，火箭候选复核未通过

模型假设机器人只要射程内有目标就停下攻击，分别采用最近目标、基地在射程内优先两种规则。训练比较混合炮台、混合＋范围选点、两火箭、三火箭，选中了两火箭方案。

| 独立复核，每方案 8 场 | 仅修阵营 | 两火箭＋范围选点 |
| --- | ---: | ---: |
| 撑过三晚 | 8 / 8 | 8 / 8 |
| 第三晚后平均基地 HP | 1460 | 1410 |
| 非法指令 | 0 | 0 |

候选最终平均少 50 HP，未采用。旧程序在这些场景中也能撑过三晚，说明模型没有重现用户说的第二晚失败。结果保留为[诊断记录](../lab/selfplay-diagnostic.json)，不据此宣称修好了生存问题。

## 第二轮：加入推进压力，内侧站位候选仍未通过

换用全新种子，保留普通模型；强压力模型改为机器人持续朝基地推进，基地在射程内时优先攻击基地且不检查墙遮挡。这是用于暴露脆弱性的假设，尚未证明是官方行为。

训练比较仅修阵营、混合炮台＋内侧炮手、两火箭＋内侧炮手、三火箭＋内侧炮手，选中了最后一种。

| 独立复核 | 仅修阵营（本版默认） | 三火箭＋内侧炮手 |
| --- | ---: | ---: |
| 普通模型：撑过第二晚 | 4 / 4 | 4 / 4 |
| 强压力模型：撑过第二晚 | 0 / 4 | 0 / 4 |
| 强压力模型：平均存活回合 | **179** | 167 |
| 两种模型合计：平均存活回合 | **284.5** | 278.5 |
| 两种模型合计：最终平均基地 HP | 677.5 | 680 |
| 非法指令 | 0 | 0 |

候选虽然最终平均多 2.5 HP，平均存活却少 6 回合，复核门槛未通过：结果中 `promotionPassed=false`、`promoted=filter_only`。没有把训练阶段胜出的策略直接部署。

仅修阵营与旧版同场比较：普通模型两者均 4 / 4 撑过第二晚，最终平均基地 HP 为 1355 对 1392.5；强压力模型两者均 0 / 4，平均存活回合为 179 对 178.75。修正减少了误选敌方波次，但这些小样本**没有证明整体生存提升**。

## 下一步最需要的实战信息

优先核对：**机器人是否能隔墙攻击基地，是否会为了路旁目标停下来。** 再取第二晚开始和基地被毁前各 2～3 回合的输入、我方动作和下一回合执行结果，用来区分炮手死亡、攻击非法、火力不足与基地直接受击。

当前三个一级炮台且没有升级收入，长期火力可能不足；这是待验证方向，不能只靠调整火箭比例认定能解决。详细问题与可转发短版见[机制清单](待确认机制.md)。

## 外部事实证据

- 检查时间：2026-09-18，Asia/Shanghai。
- 触发原因：用户提供新的实战机制，需要核对接口中的目标阵营字段及上游更新。
- 本地版本事实：本次对手为已发布提交 `1ff259b`；运行依赖仍仅为 Python 标准库。实验执行环境为 macOS / Python 3.14.6。
- 查询入口与来源：通过 GitHub API 读取上游 main 提交和 [官方接口文档](https://github.com/Tymonxiong/Competition/blob/7e629424c87f3f194d071696d3ee59a8dc2c0a75/docs/接口文档.md)。接口标记 v1.0 / 2026-09-09；上游 main 仍为 `7e629424c87f3f194d071696d3ee59a8dc2c0a75`，提交日期为 2026-09-11。
- 采用结论：`teamOur.type` 与机器人的 `targetTeam` 取值为 `challenger` / `defender`；配合用户关于双方机器人分开进攻的实测反馈，按字段相等筛选攻击目标。
- 残留风险：上游请求样例没有包含全部机器人阵营字段；尚未取得本次真实连续请求。缺失字段会在日志显示，程序不会按运动方向猜测阵营。正式波次、遇墙行为和其他结算仍需对照平台。
